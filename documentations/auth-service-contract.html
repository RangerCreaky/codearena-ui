POST /auth/google public — no JWT needed

The single entry point for all Google logins. NextAuth calls this after completing the OAuth dance with Google. FastAPI receives the id_token, verifies it with Google's public keys, extracts the user identity, and decides whether this is a new user or a returning one. Returns an access token and a flag telling the frontend where to redirect.

Request headers

Header Value Notes
Content-Type application/json Always required for POST with JSON body

Request body

Field Type Description
id_token string required The JWT that Google issued. Contains user's email, name, picture, and the sub (Google's unique user ID). NextAuth extracts this from the Google token response and forwards it here.

Service logic — step by step

  • 1
    Verify the id_token against Google's public keys using google-auth-library or manual JWKS fetch. This proves the token was actually issued by Google and hasn't been tampered with. If verification fails → 401 immediately.
  • 2
    Decode the verified payload. Extract: sub (Google's unique user ID — this is your provider_id), email, name, picture (avatar URL from Google).
  • 3
    Query: SELECT * FROM users WHERE provider = 'google' AND provider_id = sub. This is how you find returning users — by their Google ID, not email (emails can change).
  • 4a
    If no row found → new user. INSERT INTO users (email, provider, provider_id, is_guest=false). The username column is left NULL — they haven't picked one yet. The trigger auto-creates user_profiles (with Google name + picture) and user_stats rows.
  • 4b
    If row found → returning user. UPDATE users SET last_seen_at = NOW() WHERE id = ?. Nothing else changes.
  • 5
    Determine is_new_user flag: true if step 4a ran, OR if the found user has username IS NULL (they started onboarding before but never finished).
  • 6
    Generate a refresh token: create a cryptographically random string (32 bytes, hex-encoded). Hash it with SHA-256. INSERT INTO refresh_tokens (user_id, token_hash, expires_at = NOW() + 7 days, user_agent). Store the raw token in the response, never the hash.
  • 7
    Sign an access token JWT with your SECRET_KEY. Payload: sub = user_id, username, is_guest, exp = NOW() + 15min, iat = NOW().
  • 8
    Set the raw refresh token as an httpOnly, Secure, SameSite=Strict cookie on the response. Max-Age = 7 days in seconds.
  • 9
    Return 200 with the access token and the is_new_user flag in the JSON body.

Response 200

{ "access_token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1dWlkIn0.sig", "token_type": "bearer", "expires_in": 900, "is_new_user": true } Set-Cookie: refresh_token=rt_abc123...; HttpOnly; Secure; SameSite=Strict; Max-Age=604800; Path=/auth/refresh

What the frontend does with this

  • →
    Store access_token in Zustand/React state (memory only — never localStorage)
  • →
    If is_new_user: true → redirect to /onboarding
  • →
    If is_new_user: false → redirect to /dashboard

POST /auth/refresh cookie required — no JWT

Issues a new access token silently. Called automatically by the React axios interceptor whenever any API call returns 401. The user never sees this happen. Uses the httpOnly cookie (which JavaScript cannot read — the browser sends it automatically). Validates the refresh token against the database, rotates it (deletes old, inserts new), and returns a fresh access token.

Request headers

Header Value Notes
Cookie refresh_token=rt_abc123... Sent automatically by the browser. JS never touches this. FastAPI reads it server-side.

Request body

none — the refresh token comes from the cookie only

Service logic — step by step

  • 1
    Read the refresh_token value from the incoming cookie. If cookie is missing → 401.
  • 2
    Hash the raw token value with SHA-256. Query: SELECT * FROM refresh_tokens WHERE token_hash = ? AND expires_at > NOW(). If no row found → 401 (token is expired, revoked, or forged).
  • 3
    Get the user_id from the found row. Query: SELECT id, username, is_guest FROM users WHERE id = user_id AND deleted_at IS NULL. If user is deleted → 401.
  • 4
    Rotate the refresh token: generate a new random token. DELETE FROM refresh_tokens WHERE id = old_row_id. INSERT INTO refresh_tokens (user_id, token_hash=hash(new_token), expires_at = NOW() + 7 days). These two happen in a single DB transaction.
  • 5
    Sign a new access token JWT with the same payload structure: sub, username, is_guest, exp = NOW() + 15min.
  • 6
    Set the new raw refresh token as the httpOnly cookie (replaces the old one). Return the new access token in the JSON body.

Response 200

{ "access_token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1dWlkIn0.new_sig", "token_type": "bearer", "expires_in": 900 } Set-Cookie: refresh_token=rt_new_xyz...; HttpOnly; Secure; SameSite=Strict; Max-Age=604800; Path=/auth/refresh

What the frontend does with this

  • →
    Store the new access_token in memory, replacing the expired one
  • →
    Retry the original request that triggered the 401 — now with the fresh token
  • →
    User sees nothing. The whole cycle is invisible.

POST /auth/logout JWT required

Logs the user out. Revokes the refresh token in the database so it can never be used again, and clears the httpOnly cookie. The access token is left to expire naturally — at only 15 minutes it's not worth the complexity of blacklisting it. Optionally logs out all devices simultaneously with the all_devices flag.

Request headers

Header Value Notes
Authorization Bearer eyJ... Valid access token. FastAPI extracts user_id from it.
Cookie refresh_token=rt_abc... Sent automatically. Used to identify which session to delete.

Request body

Field Type Description
all_devices boolean optional Default false. If true, deletes ALL refresh token rows for this user — logs them out of every browser and device simultaneously.

Service logic — step by step

  • 1
    Verify the JWT from the Authorization header. Extract user_id. If invalid → 401.
  • 2
    Read the refresh_token cookie value. Hash it.
  • 3a
    If all_devices = false: DELETE FROM refresh_tokens WHERE token_hash = hashed_value. Only this session is killed.
  • 3b
    If all_devices = true: DELETE FROM refresh_tokens WHERE user_id = user_id. All sessions for this user are killed.
  • 4
    Set-Cookie to clear the cookie: refresh_token=; Max-Age=0; HttpOnly; Secure; Path=/auth/refresh. This removes the cookie from the browser.
  • 5
    Return 200. The access token in the frontend's memory expires naturally in ≤15 minutes.

Response 200

{ "message": "logged out" } Set-Cookie: refresh_token=; Max-Age=0; HttpOnly; Secure; Path=/auth/refresh

What the frontend does with this

  • →
    Clear the access_token from Zustand memory
  • →
    Clear any cached user data from React Query
  • →
    Redirect to /login

GET /auth/me JWT required

Returns the current user's identity from the JWT payload only. Zero database queries — everything comes from decoding the token. Used on app load and to render the nav bar (avatar, username, XP). Because it reads only the token and not the DB, it returns whatever was in the token at the time it was issued — not a live DB read. That is intentional and fine for a 15-minute window.

Request headers

Header Value Notes
Authorization Bearer eyJ... The access token. FastAPI decodes this — no DB call.

Request body

none

Service logic — step by step

  • 1
    FastAPI's get_current_user() dependency runs. It decodes the JWT using the SECRET_KEY and verifies the signature and expiry. If invalid → 401.
  • 2
    Extract fields from the decoded payload: sub (user_id), username, is_guest, exp.
  • 3
    Return them directly. No SELECT query. This is intentionally lightweight.

What the frontend does with this

  • →

  • →

  • →
    Username and user_id stored in Zustand alongside the access token

GET /users/me/username-check JWT required

Live availability check for a username. Called on every keystroke (debounced 300ms) on the onboarding screen as the user types. Validates the format first — if the format is wrong, return the error immediately without hitting the DB. Only queries the DB if the format is valid. Extremely fast — single indexed lookup on users.username.

Request headers

Header Value Notes
Authorization Bearer eyJ... Must be authenticated — guests can't pick usernames, and the check is user-specific.

Query parameters

Param Type Description
username string required The username to check. Passed as a query string: /users/me/username-check?username=naveen_k

Service logic — step by step

  • 1
    Verify JWT — extract user_id (needed to exclude their own username from the collision check).
  • 2
    Validate format with a regex before hitting the DB: ^[a-zA-Z0-9_]{3,20}$. Must be 3–20 characters, alphanumeric plus underscore only. No spaces, no hyphens, no dots. If invalid → 400 with a specific message.
  • 3
    SELECT id FROM users WHERE username = lower(input) AND id != current_user_id. The id != current_user_id exclusion handles the case where the user is re-checking their own existing username.
  • 4
    If row found → available: false. If no row → available: true.

Response 200

{ "username": "naveen_k", "available": true } or { "username": "naveen_k", "available": false, "reason": "already taken" }

What the frontend does with this

  • →
    Show a green checkmark or red cross next to the input field in real time
  • →
    Disable the submit button if available: false or if format validation failed

Error responses

POST /users/me/username JWT required

Sets the username for a newly created account. Called exactly once — when the user submits the onboarding form. After this, the user has a complete account. Re-validates availability at write time (the username could have been taken between the last check and submission). Also updates user_profiles.display_name to match if it was null or still set to the raw Google name. This endpoint is idempotent if the same username is submitted twice by the same user.

Request headers

Header Value Notes
Authorization Bearer eyJ... The user's access token. user_id extracted from here.
Content-Type application/json Required for POST with JSON body.

Request body

Field Type Description
username string required The chosen username. Same format rules: 3–20 chars, alphanumeric + underscore. Stored lowercased.

Service logic — step by step

  • 1
    Verify JWT. Extract user_id.
  • 2
    Check if this user already has a username: SELECT username FROM users WHERE id = user_id. If username IS NOT NULL → 409 with message "username already set — use PATCH /users/me/profile to change it".
  • 3
    Validate format again server-side: ^[a-zA-Z0-9_]{3,20}$. Never trust client-side validation alone.
  • 4
    Check availability one final time: SELECT id FROM users WHERE username = lower(input) AND id != user_id. If taken → 409 "username already taken". This is a race condition guard — the check endpoint is not transactional.
  • 5
    UPDATE users SET username = lower(input) WHERE id = user_id.
  • 6
    If user_profiles.display_name is still the raw Google name (first login default), update it to match the chosen username: UPDATE user_profiles SET display_name = input WHERE user_id = user_id. The user can change display_name separately later.
  • 7
    Issue a new access token with username now populated in the payload (the original token had username = null). Sign it and return it so the frontend's in-memory token is immediately up to date.

Response 200

{ "message": "username set", "username": "naveen_k", "access_token": "eyJhbGciOiJIUzI1NiJ9.eyJ1c2VybmFtZSI6Im5hdmVlbl9rIn0.sig" }

What the frontend does with this

  • →
    Replace the old access_token in Zustand with the new one (it now has username in it)
  • →
    Redirect to /dashboard — onboarding is complete
